# Stack Research

**Domínio:** Persistência de cabeçalho de OR com numeração sequencial própria (Postgres Identity) + coluna FK com backfill retroativo via Alembic + preparação mínima para integração futura com ERP Linx
**Pesquisado em:** 2026-08-04
**Confiança:** HIGH (stack já instalado e versões confirmadas em `uv.lock`; Identity/Alembic verificados na doc oficial SQLAlchemy 2.0 e em issues do próprio repositório do Alembic)

## Contexto verificado no repositório

Antes de recomendar qualquer coisa nova, confirmei o que já está instalado (`uv.lock`) e o padrão real de código já em uso — a decisão é **não adicionar nenhuma dependência nova**, apenas usar corretamente o que já existe:

| Pacote | Versão travada (`uv.lock`) | Relevância para este milestone |
|--------|------------------------------|--------------------------------|
| `sqlalchemy[asyncio]` | 2.0.49 | Suporta `Identity()` nativamente desde a série 1.4/2.0 |
| `alembic` | 1.18.4 | Versão recente; bugs antigos de autogenerate com `Identity` (2021, Alembic ≤1.4.x) já não se aplicam |
| `asyncpg` | 0.31.0 | Driver não interfere em DDL — `Identity`/`SERIAL`/backfill são só SQL, o driver os executa de forma transparente |

Também confirmei que o codebase já tem **duas convenções coexistindo** para PK autoincremento:
- `app/modules/pedidos/models.py` (tabelas do grão produto×cliente) usa `Column(...)` estilo legado (sem `Mapped[...]`)
- `app/modules/auth/models.py`, `ingestao`, `comunicacoes`, `parametros` usam `Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)`

Todas as migrations existentes com PK (`002`, `004`, `005`, `009`, `013`) usam `sa.Column("id", sa.Integer(), autoincrement=True, nullable=False)` — isso é **SERIAL implícito**, não `Identity`. O cabeçalho da OR será a primeira tabela do projeto a usar `GENERATED ... AS IDENTITY` explicitamente, porque é a primeira vez que se precisa de um `START WITH` diferente de 1 (255316).

## Recommended Stack

### Core Technologies — nada novo, apenas uso correto do existente

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| SQLAlchemy `Identity` construct | 2.0.49 (já instalado) | Declarar a PK `id` do cabeçalho como `GENERATED BY DEFAULT AS IDENTITY (START WITH 255316)` | É o mecanismo SQL-padrão (SQL:2003) para colunas autoincrementadas no Postgres 10+; substitui `SERIAL` (que é um açúcar sintático legado do Postgres, não portável e sem suporte a `START WITH` direto na coluna). A doc oficial confirma: para customizar o valor inicial, o padrão recomendado é `Column("id", Integer, Identity(start=42), primary_key=True)` — sem isso, `autoincrement=True` sozinho gera `SERIAL` a partir de 1 |
| Alembic `op.execute` + `op.alter_column` (raw SQL puro, sem lib extra) | 1.18.4 (já instalado) | Migration 015: backfill de `or_id` em `ordens_reserva` seguido de `ALTER COLUMN ... ## Ponto 1 — Identity vs Sequence vs SERIAL: qual usar e por quê

**Recomendação: `sa.Identity(start=255316)` na coluna `id`, não `Sequence` solto nem `autoincrement=True` puro.**

| Opção | O que gera no Postgres | Por que (não) usar aqui |
|-------|------------------------|--------------------------|
| `autoincrement=True` (sem `Identity`) | `SERIAL` → cria uma sequence implícita `ordens_reserva_cabecalho_id_seq` começando em **1** | Não usar: exigiria um `ALTER SEQUENCE ... RESTART WITH 255316` manual depois do `CREATE TABLE`, um passo extra e frágil (fácil esquecer, fácil rodar na ordem errada) |
| `sa.Sequence("...", start=255316)` associada à coluna via `server_default` | Sequence nomeada e independente da coluna, referenciada por `nextval()` | Não usar: é o padrão pré-SQL:2003 (Oracle-like), mais cerimônia (precisa criar a Sequence e o `server_default` separadamente) sem nenhum ganho aqui — a decisão do PROJECT.md já é explícita: "Identity... uma sequência a menos para manter" |
| `sa.Identity(start=255316)` | `id INTEGER GENERATED BY DEFAULT AS IDENTITY (START WITH 255316)` | **Recomendado.** Sintaxe SQL padrão (Postgres 10+), o `START WITH` vai direto na definição da coluna (sem `ALTER SEQUENCE` separado), e o Postgres cria e gerencia a sequence interna automaticamente — vinculada ao ciclo de vida da coluna (um `DROP TABLE` já limpa tudo) |

**`GENERATED BY DEFAULT` vs `GENERATED ALWAYS`:** usar o padrão do SQLAlchemy, que é `BY DEFAULT` (`always=False`, o default do construtor `Identity()`). Isso permite inserir um valor explícito de `id` quando necessário (ex.: em testes, em um eventual reprocessamento manual) sem precisar de `OVERRIDING SYSTEM VALUE`. `GENERATED ALWAYS` bloquearia inserts explícitos por padrão — não há motivo de negócio para essa rigidez aqui.

**Modelo (SQLAlchemy):**
```python
from sqlalchemy import Identity, Integer, String, DateTime, func
from sqlalchemy.orm import Mapped, mapped_column

class OrdemReservaCabecalho(Base):
    __tablename__ = "ordens_reserva_cabecalho"

    id: Mapped[int] = mapped_column(
        Integer, Identity(start=255316), primary_key=True
    )
    cd_prod_cor: Mapped[str] = mapped_column(String(64), nullable=False)
    tipo: Mapped[str] = mapped_column(String(8), nullable=False)
    codigo_linx: Mapped[str | None] = mapped_column(String(32), nullable=True)
    criada_em: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), nullable=False
    )
```
Seguir o estilo `Mapped[...] = mapped_column(...)` (o mesmo de `auth/models.py`, `ingestao/models.py`) para esta tabela **nova**, em vez do `Column(...)` legado usado em `pedidos/models.py` — não há necessidade de manter a inconsistência antiga para uma tabela que nasce agora, e o coding standard do projeto (consultar via Backstage MCP antes de codificar) deve confirmar qual estilo é o oficial para código novo.

**Migration (Alembic, escrita à mão):**
```python
def upgrade() -> None:
    op.create_table(
        "ordens_reserva_cabecalho",
        sa.Column("id", sa.Integer(), sa.Identity(start=255316), nullable=False),
        sa.Column("cd_prod_cor", sa.String(length=64), nullable=False),
        sa.Column("tipo", sa.String(length=8), nullable=False),
        sa.Column("codigo_linx", sa.String(length=32), nullable=True),
        sa.Column(
            "criada_em", sa.DateTime(timezone=True),
            server_default=sa.func.now(), nullable=False,
        ),
        sa.PrimaryKeyConstraint("id"),
    )
```

### Pitfall: autogenerate + Identity

Issues antigos do Alembic (ex. [`sqlalchemy/alembic#775`](https://github.com/sqlalchemy/alembic/issues/775), de 2021, contra Alembic 1.4.3/SQLAlchemy 1.4.0b1) relatavam `AttributeError` ao rodar `--autogenerate` contra tabelas com `Identity`. Essa versão é muito anterior à travada aqui (1.18.4) e o bug específico não deve mais existir. Ainda assim, discussões mais recentes (ex. [`sqlalchemy/alembic#1181`](https://github.com/sqlalchemy/alembic/discussions/1181)) mostram que o `--autogenerate` pode propor `ALTER COLUMN` espúrios para colunas `Identity` já existentes, porque o Postgres reporta opções internas da sequence (cache, minvalue etc.) que o modelo Python não declara explicitamente — gerando diffs "no-op" barulhentos.

**Mitigação para este milestone:** escrever a migration 015 manualmente (como já é o padrão do repositório — ver `014_or_por_produto.py`, também manual) em vez de confiar no `--autogenerate` para a criação da tabela com `Identity`. Isso evita depurar diffs espúrios agora. Se, em migrations futuras, o `--autogenerate` for usado e propuser um `ALTER COLUMN ordens_reserva_cabecalho.id` sem motivo aparente, é esse comportamento conhecido — revisar manualmente o diff antes de aplicar, não confiar de olhos fechados.

## Ponto 2 — Migration com backfill em SQL puro + ALTER para NOT NULL

**Recomendação: três passos na mesma migration, com `op.execute()` de SQL puro para o backfill — sem ORM, sem lib de dados adicional.**

```python
def upgrade() -> None:
    # 1) Cria o cabeçalho (Identity acima) e obtém os ids já gerados no backfill.
    op.create_table("ordens_reserva_cabecalho", ...)

    # 2) Coluna nullable primeiro — obrigatório: não dá para adicionar uma coluna
    #    NOT NULL numa tabela com linhas existentes sem um valor para preencher.
    op.add_column("ordens_reserva", sa.Column("or_id", sa.Integer(), nullable=True))

    # 3) Backfill retroativo: 1 cabeçalho por cd_prod_cor já existente em
    #    ordens_reserva, então liga cada linha ao cabeçalho correspondente.
    #    Tudo em SQL puro — evita carregar N linhas em objetos Python.
    op.execute("""
        INSERT INTO ordens_reserva_cabecalho (cd_prod_cor, tipo, criada_em)
        SELECT DISTINCT cd_prod_cor, tipo, MIN(created_at) OVER (PARTITION BY cd_prod_cor)
        FROM ordens_reserva
    """)
    op.execute("""
        UPDATE ordens_reserva o
        SET or_id = c.id
        FROM ordens_reserva_cabecalho c
        WHERE o.cd_prod_cor = c.cd_prod_cor
    """)

    # 4) Só agora, com 100% das linhas preenchidas, trava a constraint.
    op.alter_column("ordens_reserva", "or_id", nullable=False)
    op.create_foreign_key(
        "fk_ordens_reserva_or_id", "ordens_reserva", "ordens_reserva_cabecalho",
        ["or_id"], ["id"],
    )
```

**Por que SQL puro (`op.execute` com `INSERT ... SELECT` / `UPDATE ... FROM`) em vez de iterar linhas via SQLAlchemy Core/ORM:**
- É o padrão documentado do próprio Alembic (tutorial oficial e usado em produção — visto em migrations do Dify) para exatamente este cenário: adicionar coluna `NOT NULL` a tabela populada
- Uma migration roda **fora** do ciclo async da aplicação (Alembic usa uma conexão síncrona própria, mesmo num projeto async) — não há ganho em usar `AsyncSession`/ORM aqui, e usar SQL puro evita qualquer risco de trazer comportamento assíncrono para dentro do Alembic
- `INSERT ... SELECT` e `UPDATE ... FROM` são operações no servidor Postgres, sem round-trip por linha — importante mesmo que o volume atual seja pequeno, é o hábito correto a manter
- Não precisa de **nenhuma** lib de migração de dados (ex. `alembic-utils`, `sqlalchemy-utils`) — seriam over-engineering para um backfill de uma tabela

**Ordem correta dos passos é o que evita o erro mais comum:** tentar `alter_column(nullable=False)` antes do backfill quebra a migration com `NOT NULL constraint violation`, porque já existem linhas com `or_id` NULL no momento em que a constraint tenta ser aplicada — confirmado como o padrão de erro nº1 nesse tipo de migration segundo múltiplas referências (tutoriais Alembic, discussões da comunidade, migrations reais em Dify).

## Ponto 3 — Preparação para integração com barramento/ERP Linx: NÃO adicionar nada agora

**Recomendação: nenhum pacote novo.** `codigo_linx` é só uma coluna `String(32)` nullable — não é um cliente de mensageria, não é um SDK de ERP, não é um outbox pattern.

| O que poderia parecer necessário | Por que NÃO adicionar agora |
|-----------------------------------|------------------------------|
| Cliente de fila/barramento (`aio-pika`, `aiokafka`, `confluent-kafka`, SDK proprietário do ESB do projeto) | O protocolo do barramento é **desconhecido** — a equipe de TI ainda não deu acesso (ver `PROJECT.md`: "Integração efetiva com o ERP Linx... Out of Scope"). Escolher a lib errada agora significa trocar depois; escolher certo é impossível sem o contrato real. Decidir isso é trabalho do *próximo* milestone, quando o acesso existir |
| SDK do Linx | Não existe SDK Python oficial conhecido/documentado para o Linx via barramento interno do projeto — mesmo que existisse, sem acesso ao barramento não há como validar a integração agora |
| Outbox pattern / tabela de eventos (`transactional outbox`, libs como `sqlalchemy-outbox`) | Fora de escopo explícito deste milestone (ver `PROJECT.md`: "Campos de status de envio ao Linx... nova migration quando a integração for real"). Construir a infraestrutura de envio sem saber o transporte real é desenhar no vácuo |
| Qualquer serializer/schema especial para o formato do Linx (ex. lib de EDI, XML, um schema Pydantic para o payload do Linx) | O formato do `codigo_linx` é desconhecido — por isso a decisão já tomada foi `String(32)` genérico. Um serializer específico pressupõe conhecer a estrutura, que não existe ainda |

**Precedente já existente no próprio código valida essa decisão:** a integração com Databricks — que também é uma dependência externa — **não** usa o `databricks-sql-connector` oficial; usa um cliente HTTP customizado via `httpx` (já no stack) porque isso bastou para o caso de uso real (ver `.planning/codebase/INTEGRATIONS.md`, "Custom async HTTP client via `httpx` (no databricks-sql-connector dependency)"). O padrão do próprio time é: não trazer SDK de terceiro antes de precisar, resolver com o HTTP client genérico que já existe quando a hora chegar.

**Quando a integração com o Linx for desenhada** (fora deste milestone), decidir o transporte primeiro:
- Se for REST/HTTP: `httpx` (já instalado) provavelmente basta, seguindo o padrão do cliente Databricks
- Se for fila/mensageria real (o termo "barramento" sugere isso): escolher a lib então, com o protocolo real em mãos (AMQP → `aio-pika`; Kafka → `aiokafka`; proprietário → o que a do projeto IT indicar)

Isso não é procrastinação — é reconhecer que qualquer escolha de biblioteca de integração feita sem o contrato real do barramento é aposta, não engenharia.

## Alternatives Considered

| Recomendado | Alternativa | Quando a alternativa faria sentido |
|-------------|-------------|--------------------------------------|
| `Identity(start=255316)` | `Sequence` nomeada + `server_default` | Se a numeração precisasse ser compartilhada entre múltiplas tabelas (ex. um número global cross-tabelas) — não é o caso aqui, é PK de uma única tabela |
| `Identity(start=255316)` | `autoincrement=True` (SERIAL) + `ALTER SEQUENCE ... RESTART WITH 255316` manual pós-criação | Só se o projeto precisasse ficar em Postgres < 10 (não é o caso; docker-compose já usa Postgres 16-alpine) |
| Backfill via `op.execute` SQL puro | Backfill via ORM (`AsyncSession`, iterando `OrdemReserva` linha a linha) | Se a lógica de preenchimento fosse condicional e complexa demais para SQL declarativo (ex. dependesse de regra de negócio Python já implementada). Aqui o backfill é um `GROUP BY` simples — SQL puro é mais simples e mais rápido |
| Migration escrita à mão | `alembic revision --autogenerate` | Para migrations de rotina sem `Identity` (ex. adicionar uma coluna simples), autogenerate é seguro e mais rápido — o repositório já mistura os dois estilos conforme a complexidade da migration |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| `sa.Sequence` solta + `server_default=Sequence(...).next_value()` | Cerimônia extra sem ganho — duas entidades (Sequence + coluna) para gerenciar em vez de uma | `Identity()` na própria coluna |
| `autoincrement=True` sem `Identity` para esta tabela | Gera `SERIAL` começando em 1; exigiria `ALTER SEQUENCE RESTART WITH 255316` manual e frágil como passo extra | `Identity(start=255316)` |
| `alembic revision --autogenerate` para gerar a migration 015 | Risco de diff espúrio/incompleto para a coluna `Identity` recém-criada (ver pitfall acima); e o backfill (`INSERT...SELECT`, `UPDATE...FROM`) nunca é gerado por autogenerate — precisa ser escrito à mão de qualquer forma | Migration manual, seguindo o padrão já usado em `014_or_por_produto.py` |
| Qualquer SDK/cliente de mensageria (Kafka, RabbitMQ, ESB proprietário) agora | Protocolo do barramento Linx é desconhecido; TI não deu acesso ainda (fora de escopo do milestone) | Nada — decidir quando o acesso ao barramento existir |
| Campo `codigo_linx` como tipo estruturado (JSONB, enum, FK para tabela de status) | Formato do Linx desconhecido — estruturar prematuramente é a garantia de precisar migrar de novo depois | `String(32)` nullable simples, como já decidido no `PROJECT.md` |
| Carregar linhas de `ordens_reserva` em Python para calcular o backfill (`session.execute(select(...))` + loop) | Round-trip por linha, desnecessário para um `GROUP BY cd_prod_cor` que o Postgres resolve nativamente | `op.execute()` com `INSERT ... SELECT` / `UPDATE ... FROM` em SQL puro |

## Stack Patterns by Variant

**Se o coding standard do projeto (Backstage MCP) determinar usar `Column(...)` legado em vez de `Mapped[...]`/`mapped_column`:**
- Ajustar o modelo `OrdemReservaCabecalho` para o estilo de `pedidos/models.py` (`Column("id", Integer, Identity(start=255316), primary_key=True)`)
- A `Identity()` funciona igual nos dois estilos — a escolha é só de convenção de código, não afeta a DDL gerada

**Se algum dia for preciso rodar o backfill em uma tabela muito maior (não é o caso hoje, mas registrar):**
- Trocar o `UPDATE ... FROM` de passo único por lotes (`UPDATE ... WHERE id IN (SELECT ... LIMIT N)` em loop) para evitar lock de tabela longo — não necessário no volume atual do projeto
