# Quick Task 260825-f21: Excluir acesso de usuário no fluxo de alterar papel - Context

**Gathered:** 2026-08-25
**Status:** Ready for planning

<domain>
## Task Boundary

Adicionar a possibilidade de excluir o acesso de um usuário durante o fluxo de "alterar papel" na tela de gestão de usuários (`frontend/features/usuarios/ui/change-role-modal.tsx`), com o endpoint correspondente no backend (`backend/app/modules/auth/`).

</domain>

<decisions>
## Implementation Decisions

### Tipo de exclusão

- **Hard delete** do `AuthUser` (`DELETE FROM auth_users WHERE id = ...`). Justificativa confirmada: como `get_current_user` relê o usuário do banco a cada request (não há blacklist de JWT), o hard delete já corta o acesso na próxima chamada autenticada do usuário, sem trabalho extra de invalidação de sessão.

### Auto-exclusão

- **Bloquear**: um admin não pode excluir a própria conta pela tela. Endpoint deve comparar `admin.id == user_id` (mudar a dependência da rota de `dependencies=[Depends(require_admin)]` para `admin: CurrentUser = Depends(require_admin)` para ter acesso ao id do chamador) e recusar com erro claro (ex.: 400 "Não é possível excluir a própria conta").

### Local do botão e confirmação

- A ação "Excluir acesso" fica **dentro do próprio `change-role-modal.tsx`**, no rodapé, ao lado de Cancelar/Confirmar — não é uma ação separada no menu "..." da linha.
- Confirmação: **duplo clique / passo intermediário** no mesmo botão (clicar em "Excluir acesso" troca o botão para um estado "Confirmar exclusão?" — só exclui de fato no segundo clique). Sem abrir um segundo modal por cima.

### Histórico de parâmetros vinculado (FK)

- Se o usuário excluído tem `parametro_change_requests` reais associadas (`requested_by`/`reviewed_by`), **a solicitação/decisão em si permanece intacta** (chave, status, datas, payload) — só o vínculo com o usuário excluído é perdido.
- Requer **nova migration Alembic** alterando as FKs `parametro_change_requests.requested_by` e `parametro_change_requests.reviewed_by` de `AuthUser.id` para `ON DELETE SET NULL` (e tornando as colunas nullable, se ainda não forem — `reviewed_by` já é nullable hoje; `requested_by` provavelmente precisa virar nullable).
- No frontend, onde hoje `toHistoryItem`/`toRequestRow` mostram `Usuário #{req.requested_by}` / `Usuário #{req.reviewed_by}`, tratar o caso `null` exibindo **"Usuário removido"** em vez de "Usuário #null"/undefined.

### Claude's Discretion

- Nome exato do endpoint: `DELETE /api/auth/users/{user_id}` (espelha o padrão de `PUT /api/auth/users/{user_id}/roles`), `require_admin`.
- Exceção de domínio nova (ex.: `AutoExclusaoNaoPermitidaError`) seguindo o padrão de `PapeisInvalidosError`/`UsuarioNaoEncontradoError` já existentes em `domain/exceptions.py`.
- Função `deleteUser(userId: number)` em `features/usuarios/api/users.api.ts`, mesmo molde de `updateUserRole`, `method: "DELETE"`.
- Depois de excluir, a tabela de usuários deve recarregar (`users.reload()`) igual já acontece após `updateUserRole`.

</decisions>
