# Quick Task 260909-ek7: Avisos de integração crítica na aba Alertas

<objective>
Fazer o backend gerar um **aviso visível** (além do log) quando as duas integrações
críticas falharem — conexão com o Postgres (D-01) e leitura da view de estoque no
Databricks (D-02) — e expor esses avisos na aba "Alertas" já existente do frontend,
numa categoria identificável como "Problemas de integração" (D-03), com mensagem em
linguagem simples para leitor não-técnico (D-04), deduplicada por fonte e resolvida
automaticamente quando a integração volta (D-05). O aviso de **estoque/Databricks**
adicionalmente precisa aparecer **instantaneamente** para quem já está com a aba
Alertas aberta (D-07) — é o requisito mais importante da mantenedora, expresso
depois do plano inicial: instabilidade de conexão com o Databricks/API de estoque
não pode esperar um reload. O aviso de **banco de dados (Postgres)** segue só com
atualização ao recarregar a aba (D-06) — publicar esse evento pelo próprio Postgres
instável não se sustenta (ver PD-05).

Purpose: hoje as duas falhas só viram `logger.error`/`logger.warning` no servidor
(`app/modules/health/routes.py:35` e `app/workers/tasks/ingestao.py:110`) e ninguém
que usa o sistema percebe que "as informações não estão carregando" por causa de
infraestrutura. A aba Alertas é o único lugar da UI onde o analista já procura
problemas — é lá que o aviso precisa aparecer.

Output: um bounded context pequeno de avisos de integração dentro do módulo `health`
(domínio puro + aplicação + infraestrutura Redis), instrumentação dos dois pontos de
falha reais, e o `GET /api/v1/alertas` estendido com um discriminador `kind`.

Escopo: **backend apenas** (D-06). Nada no `frontend`.
</objective>

<decisoes_de_implementacao>
Escolhas de implementação feitas no planejamento, com a razão. O executor segue estas
escolhas — elas não são sugestões.

**PD-01 — O estado do aviso vive no Redis, não no Postgres.** Motivo decisivo: um aviso
que diz "o banco de dados está instável" não pode depender do banco de dados para ser
gravado ou lido (D-01). Três consequências favoráveis: (a) a falha do Databricks acontece
no processo do **worker Celery** e o `GET /api/v1/alertas` roda no processo da **API** —
o Redis já é compartilhado pelos dois (broker, streams do realtime, contadores de rate
limit); (b) nenhuma tabela nova, portanto **nenhuma migration Alembic** neste task;
(c) o aviso é *estado atual*, não histórico — o histórico é o log estruturado (D-01/D-02),
que continua sendo escrito sempre, independente do Redis.

**PD-02 — O novo bounded context mora dentro do módulo `health`.** "Estado das
integrações" é exatamente a responsabilidade do módulo que já expõe `/health/ready`, e
é lá que fica o ponto de resolução do aviso de banco. Hoje `health` é só `routes.py`;
este task o promove ao padrão DDD do projeto (`domain/` + `application/` +
`infrastructure/` + `service.py` como composition root), igual a `comunicacoes` e
`ingestao`. **Não** criar módulo `alertas` (o projeto não tem esse módulo e não é para
criar — alertas são o `alertas_router` de `pedidos`).

**PD-03 — Nenhum scheduler novo.** A resolução usa dois mecanismos periódicos que **já
existem**: o healthcheck do compose bate em `/health/ready` a cada 10s
(`.docker/docker-compose.yml:93-97`, mesmo probe usado no ECS) → resolve o aviso de
banco; o Celery beat roda a ingestão a cada 2h → a próxima leitura bem-sucedida da view
de estoque resolve o aviso de estoque. Nenhum aviso fica "preso" e nada de beat novo.

**PD-04 — Instrumentar os pontos de falha reais, três no total.** (a) o check `database`
de `/health/ready` (abre e resolve); (b) `DatabricksIngestionSource.estoque()` (abre e
resolve); (c) o `unhandled_exception_handler` que já existe em
`app/shared/errors/handlers.py`, só para exceções de **conexão** do SQLAlchemy — assim a
instabilidade que atinge um request de verdade entre dois probes também gera aviso, sem
mudar corpo nem status de nenhuma resposta.

**PD-05 — Evento realtime só para `estoque`; para `banco_de_dados` fica de fora,
deliberadamente (D-06/D-07).** O outbox do realtime (`enqueue_realtime_event(db, topic="alerts",
...)`) grava uma linha no Postgres dentro da sessão do chamador: publicar "o Postgres está
instável" através do próprio Postgres é insustentável (se a conexão está mesmo caindo, o
`commit()` desse evento tem a mesma chance de falhar que qualquer outra escrita) — por
isso a fonte `banco_de_dados` segue sem live-update, e o frontend mostra esse aviso ao
recarregar a aba (que já busca os alertas do zero).

Para `estoque` a situação é diferente: a falha acontece na **coleta** do Databricks
(`_coletar_snapshot`, antes de `_aplicar_snapshot` abrir qualquer transação de escrita —
`app/modules/ingestao/application/casos_uso.py:407-436`), então não existe uma transação
de negócio em andamento para o evento "cair junto" — o ponto de falha em
`DatabricksIngestionSource.estoque()` (`adapters.py`) não tem NENHUMA `AsyncSession` do
Postgres em escopo. A solução (D-07) é abrir uma sessão só para isso, via
`app.shared.database.session.async_session_factory` (o mesmo sessionmaker usado por
`get_db()`), publicar com `enqueue_realtime_event` e commitar essa sessão isolada — igual ao padrão
já usado em `app/modules/ingestao/application/casos_uso.py:365-383` para
`alerts.changed.v1`/`topic="alerts"`, só que fora da transação de sincronização. Best-effort
(nunca levanta): se o Postgres também estiver fora do ar nesse instante, a publicação
falha silenciosamente (`logger.warning`) e o aviso ainda existe via Redis + próxima
recarga — o live-update é um bônus, não uma dependência do fluxo principal.

**PD-06 — `estoque_virtual` não é tocado.** A instrumentação é sobre a falha de **leitura**
da view de estoque (`ler_estoque`), não sobre a projeção de estoque virtual, que segue
sendo o placebo documentado no `STATE.md`.

**PD-07 — Zero dependência nova.** Redis (`redis.asyncio`), stdlib `logging` e Pydantic v2
já estão no projeto. Nenhum `uv add`, nenhum `uv lock` — o gate de legitimidade de pacote
não se aplica a este task.
</decisoes_de_implementacao>
