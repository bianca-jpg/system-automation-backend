<objective>
Fechar SEC-06: `POST /api/auth/sign-out` passa a revogar de fato os refresh tokens vigentes do usuário.

Hoje `sign_out` é um no-op literal (`casos_uso.py:114-115`: recebe uma sessão que ignora e devolve `SignOutResponse()`), e a rota nem exige autenticação. Consequência: um refresh token roubado continua valendo 7 dias inteiros mesmo depois de o usuário clicar em "sair" — o clique só limpa o localStorage do navegador.

Desenho travado (decisão 2): corte por usuário no Redis (`auth:signed_out_since:{user_id}`), não denylist por `jti`. O access token continua válido até seu próprio `exp` de 8h depois do sign-out — **risco residual aceito e explicitamente fora do escopo desta fase**: não alterar `get_current_user`.

Contrato do frontend: `frontend/lib/api/auth-backend.ts::postSignOut` já envia `Authorization: Bearer <accessToken>` e trata resposta não-200 como best-effort. Nenhuma mudança de frontend é necessária.

Purpose: "sair" deixa de ser cosmético.
Output: `iat` no refresh token, corte no Redis, rota autenticada, testes de revogação.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| navegador/atacante → `POST /api/auth/token/refresh` | qualquer portador do refresh token obtém um par de tokens novo, sem senha |
| navegador → `POST /api/auth/sign-out` | até aqui, um endpoint não autenticado que não mudava estado nenhum |
| aplicação → Redis | passa a guardar estado de segurança (o corte); indisponibilidade precisa de política explícita |
