# Phase 20 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this is a surgical addition to ONE existing modal —
`frontend/features/pedidos/ui/modals/product-grade-detail-modal.tsx`.
No new screen, no new route. "Com Adequação" rows/products get **zero** visual
change (D-01/D-11) — every rule below applies **only** to rows where
`row.orderRef.adequacaoAplicada === false` ("Sem Adequação").

## Color

The app's semantic palette (light/dark pair) already defines exactly the
states this phase needs — reuse only, listed below with **usage restricted to
these specific elements**, per the accent-reservation rule.

| Role            | Token(s)                                                        | Usage                                                                 |
| --------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Dominant (60%)  | `--background` / `bg-card`                                         | Modal body/table background — unchanged, this phase adds no new surface  |
| Secondary (30%) | `--muted` / `bg-muted/20`, `bg-muted/40`                            | Existing header info card, table header row — unchanged                  |
| Accent (10%)    | `--primary` (via default `Button`/`Badge` styling)                  | Reserved for exactly **two** new elements: (1) the "Salvar e Aprovar OR" primary CTA button (replaces "Salvar Alterações" for in-budget sem-adequação saves), (2) the `AlertDialogAction` "Ok" button inside the new confirmation dialog. Nothing else in this phase uses accent. |
| Warning         | `--warning` (`ds-border-warning`, `bg-warning/10`, `text-warning-text`) | Budget meter at 80–99% consumed (either adição or corte); the "budget exceeded" lock banner (D-15) — see rationale below |
| Destructive     | `--destructive` (`ds-border-destructive`, `bg-destructive/10`, `text-destructive-text`) | **Not used by this phase's new elements.** Reserved exclusively for genuine request/server failures (existing `actionError`/`clients.error` banner, unchanged) |
| Neutral/healthy | `--muted-foreground` / Badge `neutral` variant                     | Budget meter at 0–79% consumed — no special color, just muted text, so a healthy budget never competes visually with the header stats |

**Why "budget exceeded" uses `warning`, not `destructive`:** the phase brief
asks this banner to match the modal's existing analog exactly
(`hasInvalidClientTotals`, line 667–671), which is itself a **blocking**
condition (it already disables "Salvar Alterações") rendered in `warning`
tone, not `destructive`. Consistency with that established local precedent
wins over an abstract "blocking = red" rule — introducing `destructive` here
would create two different visual languages for the same kind of
"this state blocks Save" condition inside one modal.

Accent reserved for: **"Salvar e Aprovar OR" button** and **the confirmation
dialog's "Ok" action** — explicitly, nothing else (not the budget meters, not
the lock banner, not any badge).

## Screen Contract — Budget Indicator (D-12 / D-13)

**Granularity:** per **row** (per client/`nr_pedido`), not one global indicator
for the whole modal. Confirmed by RESEARCH.md's architecture diagram: the
backend response embeds the aggregate budget per `nr_pedido` only for rows
where `adequacaoAplicada === false`; the frontend renders it "por linha 'sem
adequação'". A single product can have some rows "com" (no indicator at all)
and some rows "sem" (indicator shown) side by side in the same table — that
is expected and correct, not a bug.

**Placement:** inside the existing "Loja / Cliente" table cell
(`TableCell` at line 714), directly **below** the client name span, only when
`row.orderRef.adequacaoAplicada === false`. Do **not** add a new table column
— a new column would render (even if empty) for every row, including "com"
rows, which violates D-01's "zero change" for those rows. Nesting inside the
existing name cell means "com" rows are pixel-identical to today.

**Visibility:** always visible while the row is rendered (D-13 — "permanente,
visível antes de qualquer edição"), not just after the operator starts
editing. Fetch happens when the modal/row data loads, same lifecycle as
`clients.rows`.

**Structure per applicable row** (two independent meters, since D-08 says
adição/corte never compensate each other — hiding either behind a tooltip
would hide a real block condition):

```
<div className="mt-1 flex flex-col gap-1">
  {/* Adição meter */}
  <div className="flex items-center gap-1 text-[10px] font-medium text-muted-foreground">
    <span id="{rowKey}-budget-add-label">
      Adição ±5%: {consumido_adicao} de {limite_adicao} pç usadas
    </span>
  </div>
  <Progress
    aria-labelledby="{rowKey}-budget-add-label"
    value={consumido_adicao}
    max={limite_adicao}
    variant={toneFor(restante_adicao, limite_adicao)}
    className="h-1"
  />
  {/* Corte meter — identical structure, "Corte" label, restante_corte/limite_corte */}
</div>
```

**Color/tone thresholds** (drives `Progress`'s existing `variant` prop —
`default | success | warning | destructive | info`, no new variant to add):

| Consumed % of limit                         | `variant` | Rationale                                              |
| ---------------------------------------------- | ----------- | ---------------------------------------------------------- |
| 0–79%                                          | `default` (neutral) | Healthy — do not compete visually with the header stats |
| 80–99%                                         | `warning`   | Approaching the limit — same tone as the exceeded-budget lock banner, giving early warning before the hard stop |
| 100% (`restante === 0`)                        | `destructive` | Fully spent — informs the operator this specific meter cannot absorb any more of that kind of change, even before they try |

**Edge case — `limite_adicao === 0` or `limite_corte === 0`** (e.g.
`total_original` too small for `floor(total_original × tolerância)` to yield
at least 1 piece): render the meter as `variant="destructive"`, 100% filled,
with copy "Adição ±5%: 0 de 0 pç usadas" — do not hide the meter or divide by
zero; the operator needs to see this pedido simply has no room to grow/shrink
at all.

## Screen Contract — Save+Approve Confirmation (D-14)

**When it fires:** only on click of "Salvar e Aprovar OR" (the sem-adequação,
within-budget variant of the Save button) — never for "Com Adequação" rows
(D-11, unchanged two-button flow), and never when the batch would exceed the
budget (that case never reaches a confirm step — see the Lock contract below,
the button click's own validation already prevents it, same pattern
`save()` already uses for `hasInvalidClientTotals`/`isExpired`/etc. at lines
457–502).

**Component:** `ConfirmAlertModal`, imported fresh into
`product-grade-detail-modal.tsx`. Extend `ConfirmModalState['type']` with one
new value (e.g. `'salvar-aprovar'`) so the component's existing
`isConfirmation = content?.type === 'sem' || content?.type === 'com'` branch
is widened to also treat the new type as a Cancel/Ok decision (do not reuse
the literal `'sem'`/`'com'` values — those are already wired to the bulk
"Efetuar OR" flow in `orders-list.tsx` with different callbacks; reusing them
here would either require semantically overloading them or accidentally
triggering the wrong handler).

**Stacking:** this dialog opens **on top of** the already-open
`ProductGradeDetailModal` `Dialog`. This is already a proven pattern in this
codebase — `ConfirmAlertModal`'s own code comment confirms Radix's portal
ordering handles stacking without any manual `z-index`/`z-toast` hack. No new
stacking mechanism to build.

**Copy:** see Copywriting Contract table above — title "Confirmação", body
explains the save-finalizes-the-OR consequence, buttons "Cancelar"/"Ok".

**Behavior while pending:** identical to the existing `pending` prop pattern
already implemented in `ConfirmAlertModal` (Ok button shows "Processando...",
both buttons disabled, dialog does not close on backdrop/Esc while pending)
— no new pending-state UI to design.

**On confirm:** triggers the same `save()` flow already in the modal, but
that flow now also performs the approval step server-side in the same
request/transaction (backend concern, D-07/D-09 — not a UI decision). On
success, the modal closes exactly as `save()` already does today (line 543).

## Screen Contract — Budget Exceeded Lock (D-15)

**Trigger:** at least one dirty row in the batch has
`row.orderRef.adequacaoAplicada === false` AND the pending edit's delta
(`new_qty - baselineRowTotal(row)`) would exceed that row's own
`restante_adicao` (if positive delta) or `restante_corte` (if negative delta)
— computed client-side from the same budget payload used for the meters
(D-16: this is UX-only feedback; the backend remains the enforcing source of
truth and can still reject with its own error even if the frontend thought it
fit).

**What locks:**

- The Save/"Salvar e Aprovar OR" button becomes `disabled` — **exact same
  mechanism** already used for `hasInvalidClientTotals` at line 812
  (`disabled={isBusy || isExpired || dirtyCount === 0 || dirtyCount > 100 ||
  hasInvalidClientTotals || hasExceededBudgetRows}`, new condition appended
  to the existing list, not a parallel disabling mechanism).
- Quantity `Input` fields for the offending row **stay editable** — the
  operator must be able to type a smaller number to get back under budget.
  Do not disable inputs; disabling them would trap the operator in the
  blocked state with no way to self-correct.

**Banner:** `role="alert"`, rendered in the same alert-stack position as the
three existing banners (642–678), reusing `hasInvalidClientTotals`'s exact
visual pattern:

```
<div role="alert" className="mb-4 flex items-center gap-2 rounded-control border ds-border-warning bg-warning/10 p-3 text-xs font-medium text-warning-text">
  <AlertTriangle className="h-4 w-4 shrink-0 text-warning" />
  A edição de {overBudgetRows.map(r => r.client).join(', ')} ultrapassa o
  orçamento de ±5% do pedido: restam apenas {restante_adicao} pç para
  adicionar e {restante_corte} pç para cortar. Reduza a alteração para salvar.
</div>
```

**Stacking order with existing banners:** append after
`hasInvalidClientTotals` (which still applies, unchanged, to "com" rows) and
before the `dirtyCount > 100` banner — same top-to-bottom order the modal
already uses (server/conflict errors first, then realtime conflicts, then
per-row validation issues, then batch-size limits).

## Non-Goals / Guardrails

- No pixel of the "Com Adequação" rendering path changes — if a diff touches
  any class name, copy, or DOM structure reachable when
  `adequacaoAplicada === true`, that diff is out of contract (D-01/D-11).
- No new color token, spacing value, font size, or component variant is
  introduced anywhere in this phase — everything above maps to an existing
  token/variant already in `design-system/tokens/*.css` or already rendered
  elsewhere in this exact file.
- The frontend budget check is UX-only (D-16). Never treat a client-side
  "within budget" result as authorization to skip the backend's own
  validation — the confirm dialog and the lock banner are both advisory
  surfaces over a servers-side-enforced rule.
