# Milestone v1.2 — Platform Hardening / Audit Remediation

**Defined:** 2026-08-07  
**Status:** Planning only (sem execução de código de aplicação)  
**Driver:** Audit de produção/dev brownfield FastAPI — ver `.planning/research/AUDIT-2026-08-07.md`  
**Referência de padrões:** Collab API `collab-backend` (CI gates, ECS api/worker/beat, migrations no deploy, Docker prod)

## Goal

Deixar o backend automation OR **seguro o bastante para operar**, **impossível de deployar sem qualidade**, **operacionalmente completo** (worker+beat+migrations), com **imagem Docker enxuta**, **contratos front↔API honestos** e **observabilidade mínima** — alinhado ao que o Collab API já pratica.

## Non-Goals (este milestone)

- Integração barramento Linx (INTG-*)
- Edição de grade end-to-end (GRADE-*)
- Migrar auth para Cognito/Auth MS neste ciclo (avaliar em SEC; default = fail-fast JWT local + secrets obrigatórios — Cognito é melhoria futura se produto exigir)

### Phase 4: CI quality gates before deploy

**Goal:** Nenhum push em branch de deploy chega ao ECS se lint, types ou testes falharem.  
**Depends on:** Nothing (pode começar imediatamente)  
**Pattern (Collab):** `ci.yml` + jobs `quality`/`tests` como `needs:` do job `deploy` em `deploy-ecs.yaml`.  
**Success (observable):**

1. Workflow tem job(s) `quality` (ruff check + format --check + pyright) e `tests` (pytest com serviços necessários)
2. Job `deploy` declara `needs: [quality, tests]` (ou equivalente) — falha de gate = sem build ECR
3. PR / push `develop` vermelho impede imagem nova no cluster

### Phase 5: Auth / OTP / seed / JWT fail-fast security

**Goal:** Ambiente PROD (e qualquer deploy real) **recusa subir** com secrets/seed inseguros; OTP chega ao usuário.  
**Depends on:** Nothing (paralelo a Phase 4 em planejamento; execução pode ser Wave 1 junto)  
**Success:**

1. `JWT_SECRET` sem default fraco em PROD — fail-fast na boot se ausente/igual a placeholder
2. `SEED_AUTH_ON_STARTUP` default `False`; em PROD seed proibido ou exige flag explícita + allowlist de ENV
3. OTP em PROD enviado via SMTP/comunicações existentes (não só log)
4. Documentação de rotação de senhas seed / remoção de usuários default pós-hardening
5. Código OTP armazenado como hash em `auth_otp_challenges` (não plaintext) — adicionado 2026-08-12, achado de auditoria de segurança
6. `POST /api/auth/sign-out` revoga o(s) refresh token(s) vigente(s); um refresh token usado após sign-out é rejeitado — adicionado 2026-08-12
7. Rate limit (usuário+IP) em sign-in e nas confirmações de OTP (registro/recovery) — adicionado 2026-08-12

### Phase 6: Deploy worker + beat + migrations

**Goal:** Ingestão agendada e schema Alembic acompanham o deploy da API no ECS.  
**Depends on:** Phase 4 recomendada (não deployar stack maior sem gates)  
**Pattern (Collab):** task-definition manifest com `api`/`worker`/`beat`; one-off `alembic upgrade head` antes do service update.  
**Success:**

1. Pipeline atualiza (ou cria) serviços ECS worker + beat com a mesma imagem da API
2. Migrations rodam no deploy (task one-off ou step explícito) antes de estabilizar serviços
3. Beat schedule da ingestão 2h efetivamente dispara em ambiente deployado

### Phase 7: Docker prod hygiene

**Goal:** Imagem ECR sem toolchain de dev e sem contexto de build inchado/secreto.  
**Depends on:** Pode paralelizar com 6; ideal após confirmar CMD/entrypoint de prod  
**Success:**

1. Existe `.dockerignore` (raiz e/ou `.docker/`) excluindo `.git`, `.env*`, `.venv`, testes, caches, `.planning` (conforme política do time)
2. `Dockerfile` de prod usa `uv sync --frozen` **sem** `--group dev`
3. Imagem resultante sobe API (e workers) sem dependências só-de-dev

### Phase 8: Contratos front↔API (parâmetros) + docs truth

**Goal:** Front consome parâmetros da API; docs descrevem o sistema real.  
**Depends on:** Nada bloqueante no backend; coordenar PR no front  
**Success:**

1. Front deixa de hardcodar parâmetros de negócio cobertos por `GET /api/v1/parametros`
2. `docs/arquitetura.md` / `docs/api.md` não listam `alertas/` nem `history/` como módulos existentes (ou módulos são implementados — preferência: corrigir docs)
3. Checklist de contrato documentado no brief / README de integração

### Phase 9: Observability (Sentry, metrics auth, CORS)

**Goal:** Erros de prod visíveis; métricas não públicas; CORS alinhado a origens reais.  
**Depends on:** Phase 5 (secrets) útil antes de Sentry DSN  
**Success:**

1. Sentry (ou equivalente aprovado) integrado com DSN via env; sem DSN em non-prod a app sobe sem crash
2. `/metrics` exige auth (token/basic/rede interna) — não público anônimo na internet
3. `CORS_ORIGINS` em PROD lista apenas front(s) reais; fail ou warn se permanecer só localhost

## Status update — 2026-08-12

Reverificado direto no código (não apenas contra os outros docs de planning). Nenhuma destas fases passou pelo fluxo formal `/gsd-plan-phase` → `/gsd-execute-phase` (sem `*-PLAN.md`/`*-SUMMARY.md`), mas commits regulares entre o audit (2026-08-07) e agora já fecharam boa parte dos requirements por fora desse fluxo:

- **Phase 4 (CI):** `ruff check` e `pytest` já rodam em `.github/workflows/pipeline.yml` **antes** do build/push/deploy, sem `continue-on-error` — uma falha já bloqueia o deploy na prática, mesmo sem os jobs `quality`/`tests` separados com `needs:` que o desenho original previa. **Falta:** `pyright` (não configurado em lugar nenhum) e `ruff format --check`.
- **Phase 5 (Auth):** `JWT_SECRET` já falha o boot em PROD se fraco/placeholder (`settings.py:588-592`). `SEED_AUTH_ON_STARTUP` já falha o boot em PROD se `True` (`settings.py:594-595`), mas o **default global continua `True`** fora de PROD. OTP em PROD continua só logado (sem e-mail) — `SEC-03` ainda é gap real.
- **Phase 6 (Deploy worker+beat+migrations):** ✅ fechada na prática. O pipeline já atualiza `ECS_WORKER_SERVICE`, `ECS_ORDERS_WORKER_SERVICE` (terceiro serviço não documentado aqui) e `ECS_BEAT_SERVICE` com a mesma imagem da API. Migrations: **desenho diferente do planejado** — em vez de uma task one-off antes do deploy, o `CMD` do `.docker/Dockerfile` roda `alembic upgrade head && exec uvicorn ...` a cada boot de task de API (serializado por advisory lock do Postgres), com `health-check-grace-period-seconds 300` no pipeline para tolerar isso. Isso é **exatamente** o padrão que `.planning/CLAUDE-EXECUTION-BRIEF.md` (Phase 6, "Não fazer") pedia para evitar — funciona, mas é uma decisão de implementação diferente da planejada, não um gap.
- **Phase 7 (Docker hygiene):** `OPS-05` fechado (`ARG INSTALL_DEV=false` por padrão no Dockerfile; o pipeline não passa `--build-arg INSTALL_DEV=true`). `OPS-04` (`.dockerignore`) confirmado ainda ausente.
- **Phase 8 (Contratos/docs):** `CONTRACT-02` já não procede — `docs/arquitetura.md` e `docs/api.md` não listam módulos fantasma hoje (checado direto no conteúdo atual). `CONTRACT-01`/`CONTRACT-03` não verificados neste ciclo.
- **Phase 9 (Observability):** nada mudou — Sentry ausente, `/metrics` ainda público, CORS sem fail-fast em PROD.

Detalhe requirement-por-requirement em `.planning/REQUIREMENTS.md` § v1.2.
